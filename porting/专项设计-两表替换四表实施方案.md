## 一、目标形态（全量方案：20 → 16 表）

**移除 4 表**：`sheet_tansuoditushuju` / `sheet_zhandoudituhuizhi` / `sheet_zhandouditu` / `sheet_zhandouzaoyubiao`
**两表承载一切**：

```
世界地图点（地点 = 叙事地点 + 战斗场景）    ← 场景即地点（SceneName 即"详细地点"）
地图元素表（元素 = 叙事元素 + 战斗单位）    ← 单位即元素（用"元素类型"区分）
```

### 1.1 世界地图点（+7 列）

| 新列 | 类型 | 承载（原表） | 备注 |
|---|---|---|---|

| `探索更新` | text | 探索地图数据.LastUpdated | |

## 二、数据流改写清单（代码级）

| # | 模块 | 改造点 |
|---|---|---|
| 1 | `ExplorationMapManager` | `checkStructure/saveStructure` → 读写世界地图点；`checkBattleStructure/saveBattleStructure` → 读写世界点（场景行）+ 元素表（单位行） |
| 2 | `UIMap.js` | 探索分支：`EXPLORATION_Map_Data` → 世界点行；战斗分支：`COMBAT_BattleMap` → 元素表（过滤"战斗单位"+所在地点=场景）、Config（网格）→世界点场景行 |
| 3 | `UICombat.js` 及战斗逻辑全链 | 单位/状态读写 → 元素行 + `战斗数据` JSON 解析/回写（含当前行动者、回合资源） |
| 4 | 校验规则 | "元素类型"值域扩展（战斗单位）；战斗单位行的"所在地点"=场景名（场景已在地点表 → 既有校验天然可通过）；HP 等格式校验迁移 |
| 5 | 模板契约/CI/测试 | 16 表契约重编；消费点全量回归（grep `COMBAT_*` / `EXPLORATION_*`） |

**迁移成本说明**：四表**数据行均为 0（纯结构表）**——无历史数据迁移问题；改动=纯模型 + 代码层。

## 三、优缺点详解

### 3.1 优点（替换后获得）

| # | 收益 | 说明 |
|---|---|---|
| 1 | **真·单源** | 地图域只有两表；"地点"概念贯穿叙事/探索/战斗 |
| 2 | **表数 20→16** | 分组与 AI 上下文负担减轻 |
| 3 | **概念统一** | "场景即地点、单位即元素"；跨域查询（一个地点的全部数据）天然成立 |
| 4 | **体系复用** | 两表现有体系（location_id/element_id、校验、emoji、交互选项列）直接覆盖战斗 |
| 5 | **增强自动覆盖** | C/丙 的坐标/点击/图层增强自动适用于战斗单位 |
| 6 | **消重复** | LastUpdated×2、坐标×2、名称对齐等重复维护点消失 |

### 3.2 缺点（替换付出的代价）

| # | 代价 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **语义失真** | 🔴 高 | 战斗单位≠叙事元素；先攻/回合/行动者是"流程态"而非"条目"——AI 可能误把战斗单位当叙事内容维护 |
| 2 | **一地点多战斗** | 🟠 中 | 同地点多次战斗（不同布局）→ 需"场景=独立地点行"变通，地点表膨胀 |
| 3 | **高频写冲突** | 🔴 高 | 战斗每回合更新 HP/行动者/回合 → 叙事表被高频改写；与 AI 维护双写风险 |
| 4 | **AI 污染** | 🔴 高 | 大 JSON（结构）+ 战斗态进入 AI 可见表 → 上下文膨胀/误改（《评估》S2 已警告，列级屏蔽未证实） |
| 5 | **代码重写大** | 🟠 中高 | 战斗渲染+遭遇全链改写（≥4 模块）；回归面广 |
| 6 | **性能** | 🟡 低-中 | JSON 解析/大行读写 |
| 7 | **回滚困难** | 🟠 中 | 模型重构后回滚成本高 |
| 8 | **返工成本** | 🟡 低 | v3 刚并入的战斗 3 表将再次调整 |

### 3.3 减损设计（若执行全量替换，必配）

1. **写域约定**：`战斗数据`/`战斗结构` 列=「战斗系统专用·AI 禁写」（note+提示词规则）；
2. **缓存优先**：探索/战斗结构 JSON 仍优先走缓存（Chat+IndexedDB），表列作"持久备份"（S2 精神）；
3. **值域/过滤**：`元素类型` 扩展"战斗单位"；渲染/校验按分类过滤，避免叙事视图混入单位；
4. **生命周期**：战斗结束→单位行归档/清理策略（防元素表膨胀）；
5. **回归清单**：四表全部消费点 grep 列单逐项过测（酒馆实测 + 测试链）。

## 四、可行性结论（分层）

| 替换项 | 可行性 | 损失 | 说明 |
|---|---|---|---|
| 探索地图数据 → 世界点 | ✅ **高（近无损）** | 低 | 已被多文档论证 |
| 战斗地图绘制 → 世界点 | ✅ **中高（轻损）** | 一地点多场景变通；freq=0 隔离属性丢失（用写域约定补） | 场景即地点行 |
| 战斗地图（单位） → 元素表 | ⚠️ **中（有损）** | 动态行入叙事表；单位≠元素 | JSON 列可承载 |
| 战斗遭遇（状态） → 元素表 | ⚠️ **中低（损最大）** | 流程态 JSON 化；全链改写；高频写 | 逆模型处，重点防护 |
| **全量整体** | **可行但代价大** | 见 §3.2 | 工程 1.5~3 批 + 全链回归 |

## 五、两条实施路线（供拍板）

### 路线 A · 全量替换（16 表）——按要求执行版

```
批次 v5（数据层）：删 4 表迁移结构；世界点 +7 列、元素表 +5 列；契约/SQLite 全绿
批次 b5/b6（代码层）：四模块改造 + 校验/值域 + 回归
风险包：写域约定 + 缓存优先 + 单位生命周期 + 全链回归
```
- 适合：**表数极简**是硬目标；接受战斗数据有损与高回归成本。

### 路线 B · 折中替换（18 表）——稳健版（备选）

```
- 探索地图数据 + 战斗地图绘制（两张"结构仓"）→ 并入世界点（-2 表）
- 战斗地图 + 战斗遭遇（两张"动态数据表"）→ 保留（动态数据住在动态表）
```
- 适合：要单源收益、但不想让战斗动态数据进叙事表。
