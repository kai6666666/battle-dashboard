# 专项设计 · 地图功能融合评估（骰子地点功能 × DND 地图功能）

> 生成时间：2026-10-05
> 背景：探索地图数据表"补第 21 表 vs 适配层"待拍板；本次评估用户提出的"两表扩列承载渲染数据"方向。
> 证据：`map-view-model.ts` / `map-visualization.ts`（骰子）、`ExplorationMapManager.js` / `UIMap.js`（DND）、`数据库naiv1.1API.md`、双模板配置对照。

## 一、两个功能的本质：同一地点域、两种视图

| | 骰子 · 地点功能 | DND · 地图功能 |
|---|---|---|
| 定位 | **叙事清单视图** | **空间渲染视图** |
| 数据源 | 世界地图点 + 地图元素表 | 探索地图数据 / 战斗地图 3 表 + 缓存 |
| UI 形态 | 地区 tabs + 地点卡片 + emoji + 元素列表（热度排序） | SVG 整图 / 战术网格 + Token |
| 主键 | **详细地点**（全表唯一，其他表引用基准） | LocationName（地点名） |
| AI 参与 | AI 正常读写（叙事层） | 前端私有（freq=0 / skipFloors=200 防污染） |
| 语义问题 | "去哪 / 那里有什么" | "这个空间长什么样 / 我在哪" |

**结论①：可以融合**——不是两个重复功能，而是**同一地点实体的双视图**。
融合形态 = 双 Tab 视图（📋 清单视图 + 🗺️ 空间视图），共享主键（详细地点 ↔ LocationName）、共享焦点（全局数据表当前详细地点 / 当前场景）。

## 二、数据源承载方案对比（针对"两表扩列"提议）

### 前置事实（决定方案可行性）

1. **DND 渲染真实依赖 = 结构 JSON + SVG +（可选）当前显示锚点** ——坐标/几何在结构 JSON 内部，**无需拆列**；元素表坐标列只有"元素锚定增强"（二期）才需要。
2. **DND 读取链本来就以缓存为先**：Chat Metadata → IndexedDB → 表（第三备胎）→ AI 生成。**表级存储可省**（功能等价）。
3. **AI 污染风险**：世界地图点/地图元素表是**叙事表（AI 正常读写）**；探索地图数据表是 freq=0 + skipFloors=200（AI 不可见）。大 JSON（数 KB）塞进叙事表 → 上下文膨胀/被 AI 误改；**列级"不注入"屏蔽机制未证实存在**（仅表级 freq/skipFloors）。

### 三方案对比

| 维度 | S1：补第 21 表 | **S2：缓存化 + 轻量锚点（推荐）** | S3：全量扩列（用户提议原始形态） |
|---|---|---|---|
| 新表 | +1（21 表） | 0 | 0 |
| 世界地图点扩列 | 0 | **+1「当前显示」**（可选锚点） | +2（结构 JSON + 当前显示） |
| 元素表扩列 | 0 | 0（二期可选 +2 坐标/大小） | +2（坐标/大小） |
| AI 污染风险 | 0（freq=0 隔离） | ≈0（仅轻量列） | ⚠️ 高（大 JSON 进叙事表） |
| DND 代码改造 | 0 | 小（3 函数改缓存源） | 中（+列映射与读写） |
| 结构 JSON 持久性 | 表级（跨聊天可导出） | 聊天级 + 浏览器级缓存 | 表级 |
| 缺点 | 多 1 表，"叙事 2 + 渲染 1"三表并存 | 结构进聊天缓存（换聊天重置） | 上下文污染、AI 误改风险 |

### 对"相同效果"的判定（回答②）

- **可以呈现相同效果**：DND 渲染管线与存储解耦，只要按地点名可取"结构 JSON + SVG"即可渲染。
- 但"全塞表"不是最优形态——**重数据留在缓存层、轻量锚点挂表**（S2）才能既统一到两表体系、又零污染。
- 若强需求"结构 JSON 表级持久化/可导出" → 选 S1（隔离表）比 S3（污染叙事表）更稳。
