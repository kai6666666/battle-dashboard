# 专项设计 · 地图/地点数据源融合方案（两表承载 vs 渲染仓独立）

> 生成时间：2026-10-05
> 背景：用户三问——①骰子「地点功能」与 DND「地图功能」能否融合？②探索/战斗地图数据源能否改用「世界地图点 + 地图元素表」（扩坐标/SVG 列）？③多方案+优缺点。
> 证据：《专项设计-DND地图数据源详解.md》（上轮）、`features/map/map-visualization.ts`(438 行)、`features/map/map-view-model.ts`(270 行)、`render-dashboard.ts`、DND 侧 `ExplorationMapManager.js`。

## 一、现状对比（功能层）

| 维度 | 骰子「地点功能」 | DND「地图功能」 |
|---|---|---|
| 形态 | 关系浏览视图：地区 Tab → 地点列表 → 人物/元素聚类、热度排序、点击看表详情 | 视觉地图：AI 生成的 SVG 整图（探索）/ 战术网格+Token（战斗） |
| 数据源 | 世界地图点 + 地图元素表 + 角色表（实时读表） | 探索：探索地图数据(结构JSON)+SVG缓存；战斗：战斗 3 表 |
| 渲染物 | DOM 列表/卡片（emoji 标记） | SVG 图片 + Token 层 |
| 坐标 | 无 | 结构 JSON 内含（Bounding Box） |
| 交互 | 点击 → 表格详情跳转 | Token 点击 / 重绘按钮 |

**结论①**：两者天然互补（**浏览/关系** vs **视觉/战术**），融合 = "一个入口、双视图"（地区 Tab 旁挂"地图视图"，MiniMap 全屏进浏览页），不存在功能打架。

## 二、数据层可行性（回答②）

### 2.1 探索地图 —— 可行 ✅

关键事实：DND 探索渲染链的**缓存键与粒度** = 地点名（1 地点 : 1 行），与「世界地图点.详细地点」**1:1 对齐**。

| DND 需要 | 现载体 | 两表方案载体 |
|---|---|---|
| LocationName | 探索地图数据 | 世界地图点.详细地点（已有，值域一致） |
| MapStructureJSON | 探索地图数据 | 世界地图点 **+扩列** |
| LastUpdated | 探索地图数据 | 世界地图点 **+扩列** |
| 当前显示地图（覆盖锚） | 探索地图数据 | 世界地图点 **+扩列** |
| SVG 整图 | IndexedDB+Chat（键=地点名） | **不变**（缓存层与表无关） |
| 当前地点（主源） | 全局状态.当前场景 | 全局数据表.当前详细地点（映射） |

→ 扩 3 列即可承载；AI 生成管线（structure→svg）不改，只换"写回目标行"。

### 2.2 战斗地图 —— 不建议改用两表 ⚠️

- 战斗 = **遭遇场景**（临时、多单位、网格战术），不是"常驻地点"；
- Token 是"每遭遇 × 每单位 × 坐标"的行结构 → 战斗地图表天然匹配；
- 先攻/回合/阵营在战斗遭遇表 → 两表无对应语义；
- **战斗 3 表（遭遇/战斗地图/绘制）已并入基座且原样** —— 融合后效果天然一致，重造反而丢语义。
- 只需一步：场景名（SceneName）≈ 详细地点名，**天然可关联**（可选加 location_id 外键）。

### 2.3 "呈现相同效果"分两档（诚实说明）

| 档 | 含义 | 两表+扩列能否达成 |
|---|---|---|
| 档 1：AI 整图渲染（现状范式） | AI 生成手绘风 SVG 整图 + 缓存 + 覆盖锚 | ✅ 可以（10 成效果保留，只换数据宿主） |
| 档 2：坐标驱动渲染（数据库绘制） | 由房间/元素坐标**合成** SVG（可编辑、可交互） | ⚠️ 需**新写渲染器**——不属于本次融合；两表+坐标列是它的数据前置，可留门 |

## 三、多方案对比（回答③）

### 方案 1 · 全统一（两表承载一切，含战斗）
- 做法：世界地图点+元素表大扩列（结构/坐标/SVG/网格/Token 全塞），弃战斗 3 表。
- ✅ 真·单源。
- ❌ 战斗语义失真（遭遇/先攻/网格无归处）；基座 20 表重构；AI 上下文膨胀。
- **不推荐**。

### 方案 2 · 探索挂靠（★ 推荐 A：数据源统一优先）
- 做法：世界地图点 **+3 列**（MapStructureJSON / LastUpdated / 当前显示地图）；地图元素表 **+坐标类列（可选增强）**；不补 21 表；战斗保持 3 表。
- ✅ 探索"叙事+渲染"**单表单源**；表数不变（20）；扩列管线现成（v2/v3 同款）。
- ✅ 顺带消解"当前场景"字段差异（映射 当前详细地点）。
- ❌ 世界地图点变"重"（JSON 列可达几十 KB/行）；**双写方**风险（AI 叙事维护 + 前端渲染写回）→ 需约定"渲染列前端专用、AI 勿动"（note+提示词规则）。
- ❌ DND 代码需换表适配（checkStructure/saveStructure/override 三处，b5/b6 做，量小）。

### 方案 3 · 渲染仓独立（★ 推荐 B：稳妥优先）
- 做法：补**第 21 表**「探索地图数据」（原样 5 列）+ `location_id` 外键（关联世界地图点）；战斗保持 3 表。
- ✅ DND 代码**几乎零改**（表名/列名原样）；职责清晰（叙事=两表 / 渲染=独立仓）；无双写冲突。
- ❌ 非"单表源"（需 join）；多一张表（21）。
- ❌ "数据源唯一"目标打折（但链路唯一：location_id 关联）。

### 方案 4 · 渐进（3 先行 → 2 演进）
- 先走方案 3 保运行，b6 探索地图模块上线后，视 AI 负担情况把渲染列"毕业"进世界地图点（迁 21 表数据）。
- ✅ 分期风险最低；❌ 未来可能二次动表。

### 对比矩阵

| 维度 | 方案2 探索挂靠 | 方案3 渲染仓独立 | 方案4 渐进 |
|---|---|---|---|
| 数据源统一度 | ★★★ 单表 | ★★ 单链路(join) | ★★→★★★ |
| DND 代码改动 | 中（3 处适配） | 零 | 零→中 |
| 双写风险 | 有（需约定） | 无 | 无→有 |
| 表数 | 20 | 21 | 21→20 |
| 工作量 | v4 扩列 + b5/b6 适配 | v4 补表 + 关联列 | 二者叠加 |
| 回滚性 | 中 | 易 | 易 |

## 四、附带建议：地图元素表加坐标列（两方案通用、可选）

| 列 | 类型 | 用途 |
|---|---|---|
| 坐标 | coord（"x,y"） | 元素在地图上的锚点（点击交互） |
| 大小 | size（"w,h"） | 元素占地 |
| 形状 | text（rect/circle/path） | 元素几何（为档 2 留门） |

价值：地图元素从"叙事条目"升级为"可定位元素"（点击地图上的元素 → 详情）；
不做的代价：交互锚点缺失（不影响档 1 渲染）。

## 五、推荐结论

1. **探索地图**：采用 **方案 2**（世界地图点扩 3 列）——直接兑现"地图数据源统一"的战略目标，成本可控；
2. **战斗地图**：保持现成 **战斗 3 表**（已并入基座）——不迁移，仅天然关联；
3. **元素表坐标列**：建议**加**（可选增强，为交互/坐标渲染留门）；
4. 若偏保守（不动 DND 代码），退回方案 3（补 21 表 + location_id）。
