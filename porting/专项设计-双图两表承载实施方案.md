## 〇、先精确回答：丙和 C 采用两表吗？

**答：方向上是——但都限定于「探索侧」；战斗侧两者均未纳入两表。**

| 方案 | 探索侧承载 | 战斗侧承载 | 备注 |
|---|---|---|---|
| 丙方案详设 | 世界地图点（世界布点 x/y）+ 地图元素表（坐标/图标/形状）；结构走"甲/乙" | **未纳入**——战斗三表不动；"探战同构"仅指**渲染器**共用 | 丙-1 连坐标列都不依赖（图形自标记） |
| C 方案详解 | 世界地图点（结构/锚/坐标）+ 元素表（坐标/大小/图标） | **明确不动**——战斗三表原样（作为图层架构先例） | 结构列需按 S2 修正 → 走缓存 + 轻量锚 |
| 融合评估（S2★） | 「缓存化 + 轻量锚点」：结构/大图走缓存，表仅挂**轻量列** | 战斗保持三表 | 大 JSON 入叙事表有 AI 污染风险（列级屏蔽未证实） |

**结论**：丙/C 的"两表" = **探索侧的地点主数据体系**；要把**战斗图也全量纳入两表**（用户设问②）——是**超出丙/C 现有设计**的**新目标态**，本文件为其完整实施方案。

## 一、总体设计（探索 + 战斗，全量两表承载）

### 1.1 设计原则（五条）

| # | 原则 | 含义 |
|---|---|---|
| 1 | **地点=唯一挂载点** | 一切地图/战斗数据以「详细地点」（世界地图点行）关联 |
| 2 | **重轻分离** | 大 JSON / SVG / 快照 → 缓存层（Chat+IndexedDB）；表只存**轻量、可编辑、可校验**的数据 |
| 3 | **表格化优先** | 动态可维护数据（单位/状态）优先入表，走骰子系统 CRUD / 锁预检 / 校验通道 |
| 4 | **生命周期约定** | 战斗单位行 = **临时数据**（有寿命：战斗中 / 已归档），战斗结束清理或归档 |
| 5 | **双写方隔离** | 列级职责约定（AI 叙事列 vs 战斗模块列，note 标注 + 校验规则） |

### 1.2 统一数据模型

```
【世界地图点】地点主表（每地点一行）
  + 坐标           世界布点（世界总览图）
  + 当前显示        探索覆盖锚（导演强制显示）
  + 地图结构键      缓存键名 map_struct_{地点}（结构本体走缓存）※S2
  + 战斗场景册      轻量JSON：{scenes:[{name,key,grid,updated}], active:"场景名"}
                    —— 一地点多战斗场景的"册"；快照/底图大图仍走缓存

【地图元素表】元素表（每元素一行）
  + 坐标 / 大小 / 形状 / 图标     元素点位（探索+战斗场景静态物共用）
  + 【战斗扩展列（TN-1/3）】      HP / AC / 先攻 / 阵营 / 回合资源 / 是否行动者 / 生命周期

【缓存层】（Chat Metadata + IndexedDB，键=地点/场景）
  探索结构JSON · 探索SVG · 战斗底图SVG · 战斗单位快照（备份）
```

> 说明：战斗**单位行**入表 = "战斗图的 Token 层"两表化；"底图/结构" = 缓存化；"场景管理" = 场景册。三者拼合覆盖原战斗三表全部职能。

### 1.3 三种落地强度（TN-1 / TN-2 / TN-3）

| 维度 | TN-1 全表格化 | TN-2 册+快照（轻） | **TN-3 混合（推荐）** |
|---|---|---|---|
| 单位/遭遇 | 全部入元素表（扩列 ~8-10） | 走快照缓存，不入表 | **单位入元素表**（临时类型）；回合态轻量化 |
| 场景管理 | 场景册入世界点 | 场景册入世界点 | 场景册入世界点 |
| 高频状态（HP/移动/回合） | 全在表 | 全在缓存 | 表内（行更新）+ 少量地点行 JSON |
| 两表达成度 | ★★★ 最高 | ★ 挂载级 | ★★ 高 |
| AI 可见/可维护 | 全部可见 | 不可见（缓存） | 单位可见；底图/结构不可见 |
| 污染风险 | 高（需过滤/约定齐全） | ≈0 | 中（类型过滤+生命周期） |
| 工作量 | 大 | 中 | **中**（推荐） |

**TN-3 关键设计**：
- 单位 = 元素表行（`类型="战斗单位"`），战斗结束时 `生命周期` 置"已归档"或删除；
- 画廊视图**过滤规则**：`类型≠战斗单位`（或"生命战斗中的单位仅在地图视图显示"）；
- 校验规则新增：先攻格式、HP 为数值、单位所在地点存在于世界地图点；
- 卖点：**AI 能看到战斗局面**（谁在场、什么状态）——与骰子系统"AI 维护表格"哲学一致。

## 二、实施路线（五步）

| 步 | 内容 | 产出 |
|---|---|---|
| **1. 数据层（v4 批次）** | 世界地图点 +4 列（坐标/当前显示/地图结构键/战斗场景册）；元素表 +4 列（坐标/大小/形状/图标）+（TN-3）战斗扩展列；备份+契约+SQLite 验证 | 模板 v4 |
| **2. 读表适配层** | 探索三处（checkStructure/saveStructure/当前显示 override）→ 两表+缓存；battle 模块：读场景册→当前场景→缓存底图 + 元素表单位行 | dnd-map / dnd-battle 适配 |
| **3. 写回通道** | 单位移动/HP/状态 → 单行 CRUD（骰子系统通道）；回合推进 → 轻量更新（行动者标记+回合数）；锁预检注意单行性能验证 | 写回契约 |
| **4. UI 与规则** | 画廊过滤战斗单位；地图视图"战斗模式"切换；教程更新；校验规则（3 条）；热度计算排除归档单位 | UI/规则 |
| **5. 迁移与退役** | 战斗三表数据迁移（绘制→缓存键、单位行→元素表、遭遇列→元素表列）；双轨期（三表只读）；退役 | 迁移脚本 |

**验收清单（酒馆实测）**：①探索图生成→写缓存+锚点→重启读回；②战斗开局→场景册+单位行落表→渲染一致；③移动/HP 变更→行更新→刷新正确；④战斗结束→归档→画廊恢复干净；⑤AI 读取战斗单位行（触发一次）；⑥旧三表停用后全链路回归。

## 三、风险与代价（诚实清单）

| 风险 | 说明 | 对策 |
|---|---|---|
| 语义污染 | 战斗单位出现在"叙事元素"体系（画廊/教程/校验） | 类型过滤 + 生命周期 + 教程说明 |
| 双写方冲突 | AI（叙事）与战斗模块同业写元素表 | 列级职责约定 + note + 校验规则 |
| 性能 | 高频行更新走表格系统（锁预检延迟未知） | 单行更新压测；必要时"轻量更新通道" |
| 失去隔离 | 原三表（freq=0）天然隔离 AI；迁入叙事表后需重建边界 | 生命周期/类型/校验三重边界 |
| 迁移成本 | 三表数据 + 模块改造 | 双轨期 + 一次性迁移脚本；可回滚 |
| 工作量 | 相对"保留三表"为**纯增量成本**（中-大） | 与收益对照评估（见下） |

## 四、结论与建议

1. **若目标是"渲染/外观统一"** → **无需全两表**——统一渲染器（丙体系）即可，战斗三表保留最稳；
2. **若目标是"概念/表数统一"（全部地图数据归两表）** → 推荐 **TN-3 混合方案**：
   - 数据达成度高（探索+战斗单位+场景册全在表；仅重资源走缓存）；
   - 污染可控（类型/生命周期/校验三重过滤）；
   - 工作量中等，可分期（数据层 v4 → 适配层 → UI/规则 → 迁移）。
3. **无论选哪条**：先拍 **S2（探索侧缓存化+轻量锚）**——它是共同前置，且零污染；
4. TN-1（全表格化）可作 TN-3 的升级目标态；TN-2 为保守态（挂载级达成）。
