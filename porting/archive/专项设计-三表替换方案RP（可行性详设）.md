# 专项设计 · 三表替换方案 RP（可行性详设）

> 生成时间：2026-10-05
> 命题：用「**世界地图点 + 地图元素表 + ⚔️战斗遭遇表**」**替换**「🖌️战斗地图绘制 + 🗺️探索地图数据 + 🗺️战斗地图」——**必须替换可行性**。
> 结论：**可行（关键机制已验证）**——本方案记作 **RP**。
> 证据：`shujuku-naiv1.1`（数据库插件）源码、`prompt-prepare.ts`、`chat-scope-range.ts`、`sql-table-service.ts`；DND 侧 `ExplorationMapManager.js` / `UIMap.js`。

## 〇、命题澄清（丙/C 与"两表"的关系）

- 丙方案 / C 方案**部分采用**「世界地图点 + 地图元素表」：**元素层/地点层**（元素坐标、图标、地点布点）确实以此两表为数据源；
- 但丙/C **没有**主张把「探索结构 JSON / 战斗场景 / 战斗单位」全量塞进这些表——那些部分它们建议走缓存（S2）或专表（S1）；
- 本需求（**三表替换三表**）是更进一步的全量统一，记为 **RP**——以下为独立可行性论证。

## 一、机制验证（可行性依据）★核心

### 1.1 「隐藏物理列」原生机制（决定性发现）

数据库插件（shujuku-naiv1.1）**原生支持列级隐藏**——`hiddenPhysicalColumns`：

| 行为 | 说明 | 证据 |
|---|---|---|
| **AI 投影隐藏** | prompt 构造时，隐藏列**不会**发给 AI（上下文零污染） | `prompt-prepare.ts` L230："模板未声明的列合并进 hiddenPhysicalColumns，**只影响投影**，不改写持久化数据" |
| **AI 改列被阻止** | AI 的 SQL 变更触碰隐藏列 → 被断言阻止 | `sql-table-service.ts` L1046 `assertNoHiddenPhysicalColumnMutations_ACU`（L1443 在更新编排中调用） |
| **数据保留** | 持久化数据不受影响；前端可正常读写 | 同上 + `chat-scope-range.ts` L124-145 |

声明方式（两档）：
1. **显式**：模板 `sourceData.hiddenPhysicalColumns = ['列名', …]`（模板辅助 v3 已支持该键，`compiler.ts` L1231）；
2. **自动**：模板 ddl **未声明**但运行时存在的列 → 自动并入隐藏（`chat-scope-range.ts` L94）。

→ **渲染大列（结构 JSON / 场景 JSON / Token 坐标）可以做到"AI 完全看不见、改不了，但数据在表里"**。

### 1.2 表级注入/更新控制（辅助）

- `updateFrequency = 0` → **禁用该表自动更新**（`visualizer-sidebar.ts` L176 注释）；
- `sendLatestRows` → 仅发送最新 N 行；`sendRowsSqlTemplate` → 自定义发送模板（注意：**表中存在隐藏列时该自定义模板会被忽略**——安全原因，与本方案无碍：本方案就是要藏列）。

## 二、替换映射设计（三表 ← 三表）

### RP-1 探索地图数据 → 世界地图点（+ 地图元素表可选）

| 原数据（探索地图数据） | 新落点（世界地图点 +列） | 可见性 |
|---|---|---|
| LocationName | 详细地点（已有，1:1 对齐） | 叙事可见 |
| MapStructureJSON | **+列 `MapStructureJSON`** | **隐藏列**（系统维护） |
| LastUpdated | +列 `LastUpdated` | 隐藏列 |
| 当前显示地图（覆盖锚） | +列 `当前显示地图` | 隐藏列 |
| （可选二期）房间拆行 | 地图元素表（类型=房间 + 坐标列） | 增强项 |

### RP-2 战斗地图绘制 → 世界地图点（场景列，按地点缓存）

| 原数据（战斗地图绘制） | 新落点 | 可见性 |
|---|---|---|
| SceneName | = 详细地点（命名约定；多场景见 §四-缺点 3） | — |
| VisualJSON（战斗场景结构） | **+列 `战斗场景JSON`**（世界地图点） | **隐藏列** |
| GridSize | 战斗遭遇表 `网格` 列（遭遇级，见 RP-3） | 可见（轻量） |

### RP-3 战斗地图 → ⚔️战斗遭遇表（+ 列）

| 原数据（战斗地图） | 新落点（战斗遭遇表 +列） | 说明 |
|---|---|---|
| Token 行（单位名称/类型/坐标/大小/Token） | **+列 `坐标`、`大小`、`Token`** | 单位战场属性天然属于"单位行"（遭遇表）；比原表**语义更顺** |
| Config 行（网格尺寸） | +列 `网格`（遭遇级） | 一次战斗一种网格 |

**代码改造点（适配层，b5/b6 实施）**：
1. `ExplorationMapManager.checkStructure/saveStructure` → 读世界地图点（+列）；
2. `getMap` 的"当前显示"override → 读世界地图点.当前显示；
3. `checkBattleStructure/saveBattleStructure` → 读世界地图点.战斗场景JSON；
4. `UIMap.renderMiniMap` 探索段 → 同上；
5. `UIMap` 战斗段：`COMBAT_BattleMap` → `COMBAT_Encounter`（Token/网格列）；
6. 缓存键/读取优先级（Chat → IndexedDB → 表）**不变**。
> 合计约 **6-8 处**，全部为"换表名/列名"级适配。

## 四、优缺点（详细）

### 优点
1. **零污染（机制级保证）**：渲染大列=隐藏列 → AI 看不到、改不了——比"缓存化"（S2）更彻底的是**数据可持久化/可导出**；
2. **表数不增**：20 表达成探索+战斗全功能（相对"补第 21 表"方案 -1 表）；
3. **单一数据源**：地点/元素/单位三主表承载一切——"地图数据源唯一"彻底落地；
4. **语义归位**：单位坐标/Token → 遭遇表（单位属性）；比现状"战斗地图表"更顺；
5. **系统联动最顺**：画廊视图、探索渲染、战斗渲染、AI 叙事共享同键（详细地点）；
6. **复用现成机制**：hiddenPhysicalColumns/updateConfig 均为插件既有能力，无需新造轮子。

### 缺点 / 风险
1. **依赖隐藏列机制实测**（S0 必须通过；若失效 → 回退 S2/S1）；
2. **表宽增加**：世界地图点存储列变多（隐藏列不占 AI 上下文，但占表结构复杂度）；
3. **一地点多场景受限**：SceneName=详细地点约定下，主场景唯一；多布局需扩展名或元素表存"场景目录"；
4. **DND 代码 6-8 处改造** + 回归面（一次性成本，适配层风格）；
5. **导出/备份细节待验证**：隐藏列随表导出的行为（持久化目标需要它——预期包含，S0 一并测）；
6. **回滚成本**：方案落地后回退需还原三张专表结构（保留备份即可）。

## 五、与既有方案对照

| 维度 | S1 补21表 | S2 缓存化 | **RP 三表替换** |
|---|---|---|---|
| 表数 | 21 | 20 | **20** |
| 污染风险 | 零（freq=0 隔离） | 零（不进表） | **零（隐藏列）** |
| 数据持久化 | 表级 | 聊天/浏览器缓存 | **表级** |
| DND 改造 | 零 | 小 | 中（6-8 处） |
| 单一数据源 | ✗（三表并存） | 部分 | **✓（三主表）** |
| 前提 | 无 | 无 | **S0 隐藏列验证** |

> RP ≈ 「S1 的持久化 + S2 的零污染 + 单源统一」三者的上限组合——代价是代码改造量与机制依赖。

## 六、结论

1. **"必须替换"技术上成立**：核心路径（隐藏列×三重行为）已验证存在，代码改造点收敛（6-8 处）；
2. **前置条件**：S0 微验证（隐藏列三行为实测）通过——通过则 RP 为本命题最优解；
3. **实施次序建议**：RP-3（战斗单位→遭遇表，最顺）→ RP-1（探索→世界点）→ RP-2（场景→世界点）；
4. 若 S0 未通过 → 回退推荐：S2（缓存化+轻量锚点）或 S1（第 21 表）。
