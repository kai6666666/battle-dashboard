# 专项设计 · 地点功能 × 地图功能 融合方案对比（v1）

> 生成时间：2026-10-05
> 问题：① 骰子「地点功能」（数据源=世界地图点+地图元素表）与 DND「地图功能」能否融合？
> ② 探索/战斗地图数据源能否统一到「世界地图点+地图元素表」（加坐标、SVG 等列），呈现相同效果？
> ③ 多方案 + 优缺点。
> 证据：骰子侧 `features/map/map-view-model.ts`（270 行）、`map-visualization.ts`（438 行）；DND 侧见《专项设计-DND地图数据源详解.md》。

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| ① 能否融合 | **能，且天然互补**——两者是「叙事导航层 × 空间渲染层」的上下游，不是互斥功能 |
| ② 数据源统一 | **探索地图：可行**（挂到地点行即可复现）；**战斗地图：不建议全并**（模型不同构）；**元素加坐标：可作增强层**（非替代） |
| ③ 方案 | A 双表分工（低风险）｜B 单表统一（极致简表）｜C 元素坐标化（深度融合，大工程）｜**D = A+轻量增强（推荐）** |

## 二、现状对照（功能本质）

### 2.1 骰子「地点功能」= 卡片式叙事导航（acu-map-*）

- 结构：**地区 Tabs → 地点缩略图网格 → 焦点区**（选中地点的角色头像 + 元素 Chip + 信息）；
- 数据源：
  - `世界地图点`：详细地点 / 次要地区 / 地点类型 / 描述 / 重要度 / 探索状态 / emoji；
  - `地图元素表`：元素名称 / 类型 / **所在地点**（挂在该地点下）/ 状态 / 交互选项；
  - `全局数据表`：当前详细地点、当前主要地区（决定默认焦点）；
  - NPC/主角表：所在地点（算热度：角色数+元素数排序）。
- 本质：**无坐标、无画布**——回答"世界有什么、我在哪、此处有什么人/物"。

### 2.2 DND「地图功能」= 空间渲染

- 探索地图：地点 → 结构 JSON → SVG 整图（AI 生成，缓存 3 层）；
- 战斗地图：场景 → 网格 + 底图 + 单位 Token + 行动者。
- 本质：**有坐标系/画布**——回答"这个地方/这场战斗长什么样"。

### 2.3 关系判定

```
骰子地点视图（叙事数据）           DND 地图（渲染）        ← 融合后链路
┌─ 地区/地点/元素/角色 ─┐  选定地点   ┌─ 探索 SVG 图 ─┐
│  世界地图点+元素表    │ ────────→ │  战斗网格+Token │
└─（AI 高频维护）      ┘            └─（低频+缓存） ─┘
        导航/列表侧                    画布/空间侧
```
**融合形态 = 同一面板两级视图**：L1 世界视图（骰子侧，选地点）→ L2 地点视图（DND 侧，渲染当前地点）。

## 三、数据源统一可行性（问题②逐项）

### 3.1 探索地图 → 可行

- DND 渲染引擎的输入只有两个：`LocationName`（地点名）→ 结构 JSON / SVG；
- 「世界地图点」本来就"每地点一行"——**加 4 列即可承载**：`MapStructureJSON` / `MapSVG`(缓存键) / `LastUpdated` / `当前显示地图`；
- 锚点对齐：`详细地点` = `LocationName`（location_id 体系已在）；
- 代价：读表适配层做表名/列名映射；须防 AI 改写大 JSON 列（note 标注"系统维护"）。

### 3.2 战斗地图 → 部分可行，不建议全并

- 数据模型不同构：**场景（SceneName）≠ 地点**（同一地点可有多次战斗、不同布局）；
- Token 表是**动态多行数据**（单位/坐标/大小/HP 态）——塞进地点行或元素表会造成语义污染，且丢"一地点多场景"能力；
- 折中：**战斗底图（VisualJSON）可选挂到地点**（按地点缓存底图）；**Token 与遭遇层保持独立表**（基座已含 `COMBAT_BattleMap` / `COMBAT_Encounter` / `COMBAT_Map_Visuals`）。

### 3.3 元素加坐标 → 增强层可行（注意对齐风险）

- 元素表加 `x/y`（或 `gridX/gridY`）+ 图标列，可在渲染图上叠加"元素点位"（点击→元素详情/交互选项）；
- 风险：DND 探索图是 **AI 整图**，SVG 坐标系与真实坐标不保证对齐 → 点位叠加优先用于**战斗网格**（坐标系确定）或"示意列表+hover 高亮"，不强求探索图精确落点。

## 四、方案对比（问题③）

### 方案 A：双表分工（叙事表 + 专项渲染表）

| 维度 | 内容 |
|---|---|
| 数据层 | 世界地图点/元素表（叙事，原样）；**探索地图数据补为第 21 表**（原样 5 列）；战斗三表原样（已入基座） |
| 代码层 | DND 地图代码**零改造**（原表原名原列）；仅适配层映射全局表字段 |
| 优点 | 风险最低；各层独立演化；AI 维护边界清晰（叙事高频 / 渲染低频系统维护）；DND 效果 100% 保真 |
| 缺点 | 表数 21；地点名跨表关联（靠 location_id/文本对齐，可加校验规则）；"当前显示地图"与"当前详细地点"双锚点需协调 |

### 方案 B：单表统一（探索并入世界地图点）

| 维度 | 内容 |
|---|---|
| 数据层 | 世界地图点 **+5 列**（MapStructureJSON / MapSVG / LastUpdated / 当前显示地图 / 可选 GraphSize）；不建第 21 表 |
| 代码层 | 读表适配层把 `EXPLORATION_Map_Data` 映射到「世界地图点+列」 |
| 优点 | **20 表不增**；地点=一行管"叙事+渲染"；无跨表关联；"当前显示地图"可复用 |
| 缺点 | 适配层改造量中；地点表变宽（12→17 列）；AI 更新地点行有覆写大 JSON 风险；"叙事/渲染分离"原则被打破 |

### 方案 C：深度融合（元素坐标化 + 渲染引擎改造）

| 维度 | 内容 |
|---|---|
| 数据层 | 世界地图点加坐标（世界总览布点）+ 元素表加坐标/图标；探索图改为"底图 + 元素点位层"组装 |
| 代码层 | **渲染引擎大改**（整图→元素图层组装）；AI 生成管线重设计（逐元素生成+布局） |
| 优点 | 交互最强（点元素直达详情）；完全结构化；可做"世界总览图" |
| 缺点 | **工程量最大、风险最高**；手绘整图效果难以保真；坐标对齐难题；周期长 |
| 定位 | Phase 2 增强（不作为融合首期） |

### 方案 D（推荐）：A + 轻量增强 =「双轨 + 增强层」

| 维度 | 内容 |
|---|---|
| 数据层 | 方案 A 全量；**另加坐标列（可空）占位**：世界地图点 +x/y，元素表 +x/y/icon（本批不加渲染依赖） |
| 代码层 | A 的适配层 + **UI 联动**：骰子世界视图选地点 → DND 地图渲染该地点（左列表右画布，b4/b10 排期） |
| 优点 | 零改造保真 + 融合体验兼得；坐标列一次到位（扩列成本低）；为 Phase 2 留全部门 |
| 缺点 | 混合形态，联动层要写（工作量中等）；需 UI 归属拍板 |

### 反例 E：全量并入（探索+战斗+单位全塞世界地图点/元素表）

- 结论：**不可行**。战斗非地点同构、Token 动态多行、一地点多场景丢失、渲染引擎必大改——已排除。

## 五、方案对比一张表

| 维度 | A 双表分工 | B 单表统一 | C 深度融合 | D（推荐）A+增强 |
|---|---|---|---|---|
| 表数 | 21 | 20 | 20 | 21 |
| DND 代码改造 | 零 | 适配层中 | 重构大 | 零+联动 |
| 效果保真 | 100% | 100%* | 中（重构风险） | 100% |
| AI 维护风险 | 低 | 中（宽表混写） | 低 | 低 |
| 元素交互增强 | 无 | 无 | 强 | 中（Phase2 升级） |
| 工程量 | 小 | 小-中 | 大 | 中 |
| 风险 | 低 | 中 | 高 | 低-中 |

*B 需适配层正确映射；表宽与混写是主要风险点。

## 六、推荐与待拍板

**推荐：方案 D（= A 数据层 + 坐标列占位 + UI 联动）**，分期：
1. **首期（数据层）**：探索地图数据补第 21 表（A）；世界地图点/元素表加坐标列（可空，占位）；
2. **二期（代码层）**：读表适配层（全局表字段映射：当前详细地点→当前场景 等）；
3. **三期（UI）**：世界视图 ↔ 地图渲染联动（b10 面板）；Phase 2 再评估元素点位/总览图。

**待拍板**：
- P1：探索渲染数据载体 → **A（第 21 表）** 还是 **B（并入世界地图点）**？【推荐 A】
- P2：坐标列（世界点 x/y、元素 x/y/icon）→ 现在加（占位）还是 Phase 2？【推荐现在加】
- P3：UI 联动落点 → b10 面板批次确认？
